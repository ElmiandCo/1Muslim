# Profile privacy: staged interface for #1638

Status: **release-blocking; privacy is not fixed.** Baseline: `365dffb40254988be725a0bc34a7dc1a74e1db10` (local `release/v3.9`). This change adds an unused interface only. It neither modifies the existing views nor changes `profiles` grants/RLS; existing direct REST, search, view and app exposures remain. No migration has been applied. The supplied issue snapshot reports live catalog observations; this offline audit did not independently connect to that database.

## Threat matrix

| Principal / access | Existing risk or dependency | Intended staged projection |
| --- | --- | --- |
| Anonymous, direct `profiles` / old views | Verify actual grants, column grants, RLS and view owner on staging; issue reports old public views leak hidden IDs and unconsented countries. Do not assume an anon table grant. | No `anon` or `PUBLIC` SELECT grant. Verify effective privileges, including inherited roles. |
| Authenticated, direct `profiles` / REST | Issue reports table SELECT and `USING (true)` permit direct reads, bypassing client masking. Revoking table SELECT alone may leave column grants or inherited privileges; changing RLS alone does not remove a grant. | Unchanged: still exposed until grants/policies and all consumers are safely migrated. |
| Authenticated, another member through new view | An opt-in member may expose their country and display name; hidden/null ID preference must not expose username or match username filters. | Only `directory_visible IS TRUE` and non-null `consented_at` rows, with `username` masked unless `hide_1muslim_id IS FALSE`. No city, state, consent timestamp or other columns. Search/filter the projected fields, never the underlying username. |
| Authenticated self | Private profile editing, self reads, username management and permission preferences require self access. | New directory is not a self-profile interface; non-opted-in owners do not appear there. Retain an independently authorized self-only read/write path. |
| Service/admin | Privileged routes can bypass RLS; accidental response fields or search matches still expose data. | New view does not restrict service-role queries; audit and explicitly authorize/mask each privileged response. |

`profile_directory_safe_v1` is an additive, country-only opt-in interface, not a general public profile replacement. It deliberately grants authenticated access only and requires its owner to have appropriate source privileges. Review whether existing country-level consent covers subsequent changes to `profiles.country`, since the consent table does not store a consented country. Confirm owner, ownership changes, default privileges, role inheritance, view security behavior and RLS on the actual staging schema. Verify that the result and query predicates never reveal excluded data, including after opt-out. Missing schema/privileges must fail closed; do not bypass consent with a fallback.

## Consumer audit and migration blockers

The checked-in migrations do not define `member_directory`, `umma_public_profiles`, the base `profiles` table, or its complete grants/policies. Capture their actual definitions and dependencies on staging, including view owner/options, relation and column privileges, role memberships, all policies, functions, triggers and PostgREST relationship/embedded selects. The issue's catalog observations are not a substitute for this environment-specific inventory. `rg -n 'profiles|member_directory|umma_public_profiles' app supabase` is a starting point; inspect SQL, dynamic queries, RPCs, and server code too. Many callers rely on broad access:

- **Self / follow:** `app/profile/page.tsx` uses `select('*')` for both self and other members, edits identity and checks username uniqueness; `app/ashab/page.tsx` reads other profiles after relationship RPCs. A self-only rule without replacement breaks member profiles and follows.
- **Login / account creation:** `app/auth/page.tsx` currently calls password sign-in with email; `app/auth/callback/route.ts` reads the owner's profile and queries username availability. No login-by-ID resolver was established in this targeted source audit; inventory all auth/RPC paths and prove any intended resolver works without exposing IDs or enabling account enumeration before restricting access.
- **Spotlight / public posts:** `app/profile/page.tsx`, `app/components/ProfileCinematicPosts.tsx`, and `app/api/community-posts/route.ts` rely on profile data. Spotlight records have separate public read and owner write policies in `20261123031500_profile_page_posts_spotlight.sql`; validate its rendering and both anonymous and signed-in paths when changing profile access. Public author projections need their own contract; this opt-in country view would omit non-opted-in authors.
- **Map:** `app/api/member-regions/people/route.ts` uses a service role, checks both consent fields, then masks the ID; `app/api/member-regions/route.ts` handles aggregate regions. `app/components/RegionDiscovery.tsx` reads/writes the owner's region. Review opt-in withdrawal races and map PR #1633 in integration, including aggregate-versus-identity consent and mobile behavior.
- **Search / gallery:** `app/api/hub-search/route.ts` searches and returns usernames without checking `hide_1muslim_id`; `app/find/page.tsx` reads/searches city, state and country without the directory consent gate; `app/lib/discover-search.ts` and messaging search query raw usernames even when later filtering results. `app/components/CanvasUmmaGallery.tsx` queries `umma_public_profiles` and also reads `profiles` directly for rankings. Profile draft #1632 and other release drafts require combined review. Client-side filters do not protect direct queries or server search results.
- **Direct REST and joins:** PostgREST table endpoints, embedded `profiles(...)` (for example `app/components/StoriesRail.tsx`), column grants and RPCs need explicit denial tests. A safe view alone cannot prevent direct or inference queries. Avoid repointing generic authors, follow, or self consumers to this narrower country directory.

## Required staging gate and rollback

1. Compare the full open draft file lists/diffs and integrate with profile/map owners. The offline snapshot did not provide PR diffs; no conflict or integrated pass is asserted.
2. In an isolated server-backed disposable Postgres database, `psql -X -v ON_ERROR_STOP=1 -f scripts/profile-directory-safe.test.sql` exercises the fixture, view ACLs, direct-access gap, consent revocation and preference RLS. It creates roles and tables and **must never run on staging/production data**. The local socket restriction prevented this role test. `scripts/profile-directory-safe.test.sh` runs only projection expressions on disposable local Postgres in single-user mode; it cannot test permissions or RLS.
3. On staging with representative synthetic accounts, verify actual anonymous/authenticated/self/service REST queries, column grants, inherited roles, old and new views, hidden-ID search predicates, missing/false/revoked/null consent, country changes, pagination, joins and repeated requests. Confirm no private data in responses/logs. Test account recovery, sign-in, uniqueness, profile editing, follows, Spotlight, posts, map and search in mobile and desktop together with release drafts.
4. Design and review separate general public-author, directory and self contracts; migrate and test every dependent consumer and privileged endpoint before changing `profiles` grants/policies or old views. Capture current grants, policies, views and dependencies before any proposed change; document forward/rollback SQL and test restoration in staging. Re-run the full threat matrix before any deployment. Restricting only a view is not sufficient.
5. Rollback this additive interface, if applied in staging before consumers are migrated: `DROP VIEW public.profile_directory_safe_v1 RESTRICT;` (never `CASCADE`). Once consumers exist, first revert them and verify dependencies before dropping it. This rollback does not fix or change existing leaks.
